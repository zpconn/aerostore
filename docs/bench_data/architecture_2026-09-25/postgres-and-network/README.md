PostgreSQL ran as a native process on the same WSL host and filesystem as AeroStore, through a private Unix socket. This comparison does not use the earlier Docker fixture. PostgreSQL 16.13 was built from the [official source release](https://ftp.postgresql.org/pub/source/v16.13/) after verifying its published SHA256, with `--without-readline --without-icu` and the recorded GCC `-O2` flags. This synthetic fixture uses integer/boolean columns. [Resource and build metadata](postgres-native/resource.json), configure/build/install logs, and [actual server settings](postgres-native/settings.json) preserve those choices; binaries, source archives and database files are excluded. Resource status and PID describe the capture time, not a promise that the fixture remains running.

The PostgreSQL baseline uses SERIALIZABLE transactions, query-discovered writes and the explicitly selected buffered adapter: complete SQL predicate reads, snapshot-local point-read caching, an overlay with read-your-writes and savepoint rollback, sorted locking of discovered rows at commit, and one prepared set-based update. The eight live tests cover competing empty searches, predicate entry/exit, global queries, integer boundaries, concurrent opposite write orders, atomic failure cleanup and fixture ownership. Immediate-write mode remains available as a sensitivity; both modes now share the revised indexes. Sample EXPLAIN plans in the scenario report are literal custom plans, not steady-state prepared generic-plan measurements or execution profiles.

Business acknowledgements remain asynchronous. PostgreSQL had `fsync=on`, `full_page_writes=on`, `synchronous_commit=off`, `wal_writer_delay=10s` and `deadlock_timeout=10ms`. After work completes, its owned one-row `drain_fence` update uses `synchronous_commit=on` and verifies that the previously sampled WAL insertion position has flushed. A failed fence fails the run. This actively drains work rather than waiting for the periodic writer; its cost belongs in the separately reported completion drain. It does not establish equal crash-loss windows, recovery behavior or synchronous message acknowledgement across engines.

The loopback bundle includes the actual [client setup](remote-loopback/client-setup.json), [server final state](remote-loopback/client-final.json), [40-message history](remote-loopback/history.jsonl), orchestration manifest, completion marker, supervisor records and logs. Server setup/final copies were JSON-equivalent and are omitted to avoid duplication; the manifest names their archived equivalents. Top-level reports and logs are retained for the 20 bounded scenarios; their larger raw per-scenario histories remain at the original evidence paths and are not copied here.

The remote lifecycle check placed all processes on one host. No SSH host was invoked. Its successful shutdown had zero active sessions, zero remaining registrations and no backend failures. Separate local process tests verify that the independent Linux Python supervisor kills and reaps an orphaned descendant and enforces its owner deadline. The helper can orchestrate an explicitly supplied SSH host, but the service RPC has no authentication or TLS and is limited to a trusted test network. TCP connectivity and this loopback result do not establish distinct physical hosts, MMHF behavior, sustained capacity, failure-isolation acceptance or the project's 10× target.
