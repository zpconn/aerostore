# Next bounded milestone after signature affinity

Implement complete scheduled maintenance jobs at the existing worker scale, with resource admission checks prepared for later 100/200/300-worker experiments. Preserve the current one-batch profile as a control. Do not change production indexing or mutation ownership in this increment. The useful result is evidence about foreground latency, maintenance completion, conflict causes and resources under a less simplified workload; it is not yet the 10× result.

This is a read-only review of `contention_crucible/{model,calibrated,workers,runner,service,oracle}.rs`, the native and PostgreSQL adapters, `procarray.rs`, skiplist epoch registration, and the qualification driver at source `fef4c866ad708e8d49335f6432a0ce0e24d288b4232e87efece565d22ad3c32e`. No fixture or source was changed.

## Complete jobs through bounded transactions

Today a projection tick observes the complete `GlobalDue` result and processes four events; housekeeping observes `GlobalExpired` and processes 32 records. Start with those same batch sizes. A job should retain its original scheduled timestamp/cutoff, repeatedly open a new transaction, discover the current eligible rows, select its bounded batch, and commit. Finish only after a successful transaction observes the complete eligible result empty. A short batch alone is not the termination check.

Maintenance transaction granularity has not been operator-confirmed. This per-batch sweep is an explicit candidate simulation contract; it must not silently stand in for a real HyperFeed job that commits its entire sweep atomically. Confirm that boundary before calling these jobs representative, and retain a separately labeled alternative if needed.

Define completion precisely: the empty query is a serializable observation at one transaction's position in the history. The whole sweep is not an atomic snapshot of the database. A concurrent or delayed foreground transaction may create eligible work after that observation; it belongs to a later sweep under this proposed contract. If HyperFeed requires a stronger epoch/watermark guarantee, establish that requirement before claiming equivalence. Do not extend an unbounded snapshot or prelock all discovered rows to obtain a stronger guarantee accidentally.

Projection currently reschedules a selected event after its fixed cutoff, and housekeeping deactivates selected records. Those properties make repeated batches progress in a quiescent fixture. Check them explicitly. Keep transaction retries confined to the failed batch; previously committed batches remain committed. Preserve FIFO between jobs on each maintenance worker while foreground and the other maintenance worker continue. Every independent timer tick remains admitted, including ticks queued behind a slow sweep. A deadline, batch cap, retry limit, or unfinished terminal query is an incomplete job with retained partial effects, never a successful truncated sweep.

Seed multiple expiry-age cohorts so different real timer deadlines expose fresh eligible housekeeping work. Otherwise the first full sweep consumes all initially old records and the second tick becomes empty. Empty jobs are valid execution, but do not count them as repeated useful maintenance coverage. Keep the age distribution explicit and synthetic; continued population turnover is a subsequent obligation.

## Accounting and the oracle must change together

Separate fixed offered **jobs/messages** from actual **transactions**. Use an unambiguous `(job_id, batch_ordinal)` identity, stable across retries and disjoint from foreground IDs. Record every successful batch, including the terminal empty transaction, in the existing serial-history checker; retain job start/end, original deadline, effects, retries, and terminal witness. Prior committed batches cannot be erased if a later batch fails.

The current gate requires commits equal offered messages and compares deterministic per-worker event streams. A full sweep cannot keep that assumption: concurrent valid transaction orders can produce different numbers of batches. Match full/metrics companions by exact foreground corpus, scheduled jobs, cutoffs, batch policy, sources and binary, while checking each actual transaction history independently. Never require identical discovered write sets or identical batch counts across engines. No history window may be called complete by dropping transactions that cross its boundary.

Measure foreground queueing-inclusive p99 separately from whole-job maintenance latency. Report jobs due/completed/unfinished, batches, terminal probes, useful rows, retries, queue depth and oldest queued-job age. Keep the continuous admission-to-confirmed-drain denominator; extra batch transactions must not inflate useful input messages/second. Expose startup/seed cost separately. Retain failures and unknown service commit outcomes; do not automatically replay an ambiguously committed batch.

Useful tests include: more eligible records than one batch; more than one family; terminal-empty conflict and retry; foreground refresh/cancel/create around a sweep; a due-row insertion after a successful empty observation; projection and housekeeping overlapping; a paused maintenance worker spanning several ticks and admission end; and a cap failure after earlier batches committed. Full histories must remain Valid, and negative controls must reject omitted batches, changed cutoffs and a falsely asserted terminal-empty result. Re-run selected service client-disconnect cuts between batches and around commit replies; this does not fix direct-access worker-death availability.

## Review resource limits before raising worker limits

| Current bound | Prerequisite |
| --- | --- |
| 32 foreground workers, 1,024 logical families; calibrated adds two maintenance workers | Raise coordinated Rust/Python/remote limits only after startup, idle-worker, exact-count and cleanup tests. Use enough offered identities/signatures to exercise workers; report actual skew and activity. |
| 256 shared ProcArray registrations | Transactions and temporary skiplist scan epochs share this pool. Audit maximum simultaneous registrations per execution path and reserve internal headroom. The adapter currently treats exhaustion as fatal. A 300-input-worker test requires explicit bounded execution admission or a separately reviewed engine change, not a larger CLI maximum alone. |
| Service defaults to 128 sessions, one executor thread per session | Distinguish connected clients from simultaneous transactions. Bound session/executor/outcome resources and test exhaustion, cancellation and permit release. An admission design must not give application processes an unrecoverable shared permit; survivor continuity remains required. |
| Native fixture WAL: 16 × 65,536-byte slots; existing codec check covers 128 final row writes | Keep individual batches within measured encoding bounds, including framing and full-value fallback. Job size can exceed one WAL slot only because it is multiple transactions. |
| Complete service query replies have an 8 MiB frame limit | Measure worst query-result encoding at the proposed population. Do not silently truncate query results to fit the transport. Paging, if needed, needs an explicit complete-query/consistency contract. |

Also preflight PostgreSQL connection capacity with maintenance/observer headroom; OS process/thread/file-descriptor limits; native arena and retention headroom; service transaction timeouts; and history/oracle memory and search budget. The coordinator and workers each add reader threads, and service mode adds executors, so process-worker count is not a CPU/resource budget. Record exhaustion separately from serialization conflicts, and include admission waiting in message latency. Test bounded admission with simultaneous begin-plus-index-scan demand before trusting nominal worker support.

Repeated global queries can inspect the shrinking eligible population once per batch, approaching quadratic total row visits for a large quiescent job. Measure returned rows, bytes, scan time and retry work before choosing keyset pagination, index versioning, finer conflict tracking or an owner-side command batch. Those are candidate follow-ups, not presumed wins.

After full-job tests pass, progress from small concurrency to 100, then 200/300 connected input workers with declared active-execution limits and enforced host resource budgets. Keep affinity/identity controls and matched transaction, acknowledgment and drain contracts. Select each engine's efficient worker count from measurements; historical PostgreSQL worker counts are operating points, not a requirement that AeroStore use the same count. Controlled sustained trials, calibrated turnover/fork populations, survivor availability and eventual physical MMHF tests remain necessary before qualifying 10× useful foreground throughput.
